# 重构执行计划与边界

## 已完成的结构调整

1. 建立独立 Git 仓库，删除旧交付目录、镜像资产和工具下载器。
2. 前端、API、数据库迁移和维护循环合并到一个 `app` 镜像。
3. scan、image、trivy worker 合并到一个 `scanner` 镜像。
4. Java 与 Ghidra 保持独立，避免把大型工具链塞进业务镜像。
5. 删除 Trivy 数据库管理 API、维护 worker、前端操作页及相关表。
6. 用一个只读 Bundle 同时固定 Trivy 主库与 Java 库，并在报告中记录统一 Bundle ID。
7. 建立源码包和镜像包两套独立哈希、导入和验收流程。

## 后续版本建议

1. 在真实检测机完成一次从空 Docker Desktop 到全流程扫描的录像和命令输出归档。
2. 为外部基础镜像各自建立独立源码仓库和 SBOM，而不是放回本业务源码 ZIP。
3. 根据甲方硬件确定 `linux/amd64` 是否需要增加 `linux/arm64`，不要在同一验收版本中临时混用架构。
4. 压测 2 GB 上传、10 GB 展开上限和 Ghidra/Java 并发，依据结果调整 Compose 资源限制。
5. 若甲方将进程级解包隔离列为强制项，再引入按任务启动的短生命周期容器，不增加默认长期服务数量。
