1. 需求背景与目标

BinaryScan 是离线部署的二进制/容器/归档安全检测平台,检测结果通过报告交付。两个需求来自实际交付场景:

  • 需求 1:检测报告要求中文展示,并新增 Word 格式导出。当前 C/Java checker 产出的检测消息为英文,报告仅支持 JSON/HTML 两种格式,交付物缺少中文可读性与可编辑的 Office 格式。
  • 需求 2:以压缩包(含 ISO 光盘镜像)形式上传的批量二进制检测,需要一个"批次总报告"导出,汇总该批次下所有任务的检测结论,而不是逐任务打开报告。

2. 需求合理性分析

2.1 需求 1:中文 + Word

维度评估说明
业务价值高检测交付物面向中文审阅者;Word 是标准交付格式,可编辑、可归档、可盖章
合理性合理报告壳(章节标题等)原本已是中文;缺口在检测消息与交付格式,补齐后自洽
方案取舍明确展示层翻译(不动 checker 存储/历史数据)vs checker 源头中文化(需重建镜像、污染历史数据语义)——选择前者
技术可行性高docx 本质是 ZIP+OOXML,Go 标准库即可生成,不引入第三方依赖,符合离线构建约束

2.2 需求 2:批次总报告

维度评估说明
业务价值高批量检测(一个压缩包 10~20 个二进制)的交付需要一份统一结论,逐任务查看成本高
合理性合理批次 → 条目 → 任务的数据链已存在(archive_import_entries.task_id),聚合是自然延伸
技术可行性高全部数据在现有表;汇总报告可复用需求 1 的 HTML/Word 渲染体系
边界需明确汇总粒度:每任务一行摘要(状态/风险/发现数)+ 任务报告链接,不嵌入完整报告,避免文档膨胀

3. 现状调研

3.1 报告体系

  • 报告生成:后端 internal/report,按任务生成,格式 json / html(需求 1 后新增 docx)
  • 报告 API:POST /tasks/{id}/reports、GET /tasks/{id}/reports、GET /tasks/{id}/reports/{rid}/download?encoding=gzip|identity
  • HTML 模板:章节已是中文(lang="zh-CN"、任务/输入/风险/原始样本等)
  • 下载控件:ReportResultWorkspace + ReportDownloadControl,JSON 支持原始/压缩两种编码

3.2 检测消息语言

  • c-checker:15 条规则(cwe-242-gets … cwe-732-permissions)+ 系统消息(syntax_error、function_analysis_error、analysis_timeout),消息为英文
  • java-checker:13 条规则(java-weak-message-digest … java-insecure-cookie)+ 系统消息(parser_failed、java_parse_problem 等),消息为英文
  • 消息带上下文(函数名、行号等参数),不适合整句硬翻译 → 采用规则/诊断 code 级中文标题 + 原文保留策略

3.3 约束

  • 离线构建:GOPROXY=off、go mod download --network=none、前端 npm 离线 → 禁止新增第三方依赖
  • 数据库格式约束:chk_reports_format(json/html)、chk_archive_imports_root_format 等 CHECK 约束,新增格式需迁移
  • 数据契约:JSON 报告字段名与 message 原文保持稳定,历史数据不受展示层影响

5. 需求 2:压缩包批次总报告导出

状态:待实施

5.1 目标与边界

  • 目标:对一次归档导入批次(压缩包/ISO)生成一份总报告,汇总该批次全部条目的检测结论
  • 边界(不做):不嵌入各任务完整报告全文;不做批次报告的历史版本管理(与任务报告一致,按需生成即可);不改变现有逐任务报告

5.2 方案设计

数据链(已存在,无需迁移)

archive_imports(批次) ──1:N── archive_import_entries(条目,含 task_id)
                                        │
                                        └── tasks(任务) ──1:N── analyzer_runs / vulnerability_findings / reports

每条目已关联 task_id(archiveimport/repository.go),报告按任务生成。总报告 = 批次元信息 + 条目摘要(文件名、识别格式、任务状态、风险、C/Java 发现数、漏洞数)+ 各任务报告链接。

API 草案

POST   /api/v1/archive-imports/{importId}/reports      # 生成 {format: json|html|docx}
GET    /api/v1/archive-imports/{importId}/reports      # 列表(状态:queued/generating/complete/failed)
GET    /api/v1/archive-imports/{importId}/reports/{rid}/download

模块规划

任务内容涉及
R1 聚合查询批次 → 条目 → 任务状态/风险/发现计数/漏洞计数 的只读聚合新增 internal/batchreport(repository + service),或复用 report 服务扩展
R2 摘要渲染HTML 模板(批次头部 + 汇总表 + 状态图例);docx 复用 docxDocument(标题/表格)新包内 html.go/docx.go
R3 API 接入路由、CSRF、幂等键(与任务报告一致)、错误映射internal/api/batchreport.go
R4 存储新增 batch_reports 表(批次、格式、状态、artifact 引用)+ 迁移 00038db/migrations/00038_batch_reports.sql
R5 前端入口归档导入工作区新增"批次总报告"区域:生成/下载 json/html/docxArchiveImportWorkspace.vue + 类型
R6 测试聚合查询、渲染、API、前端组件单测 + 端到端各层测试文件

5.3 实施步骤与顺序

  1. R1+R4(聚合查询 + 表/迁移)——数据层,先行
  2. R2(HTML/docx 渲染)——复用需求 1 的 docxDocument 与翻译词表
  3. R3(API)——仿任务报告 handler
  4. R5(前端)——归档工作区入口
  5. R6(测试 + 端到端:上传 zip/iso → 建任务 → 生成总报告 → 下载验证)

7. 风险与缓解

风险等级缓解
docx 兼容性(样式表/复杂表格在旧版 Office/WPS 的差异)中只用基础 OOXML(标题/段落/边框表格);端到端解包验证;必要时加 styles.xml
批次条目/任务数超限导致报告过大中聚合查询设条目上限(如 1000),超限截断并标注;摘要不嵌入全文
新表/新格式的离线迁移失败低goose Up/Down 对称;迁移在 app 启动自动应用;数据库单测覆盖版本号
词表与 checker 规则不同步(新增规则)低未命中回退原文的兜底策略;词表集中维护并加一致性测试
需求 1 的偶发超时测试(archivesandbox/extract)低已知与本需求无关的并行资源竞争,单独重跑全绿

8. 验证策略

  • 单元:翻译映射(已知/未知/空/重复)、docx zip 结构与 XML 转义、聚合查询限额、迁移版本
  • 组件:web vitest(报告控件三格式、批次工作区入口)
  • 端到端:真实环境上传 zip/iso → 批量建任务 → 生成 HTML/Word 总报告 → 下载并解包校验结构与中文内容
  • 回归:go test ./... + web 全量;已知偶发超时单独重跑确认

C. 与既有契约的兼容性

  • JSON 报告字段名与 message 原文不变;中文标题仅出现在 HTML/Word 展示与前端界面
  • 历史任务报告不受影响;docx 仅对新生成的报告可用
  • 批次总报告为新增能力,不改变现有逐任务报告与归档导入流程
